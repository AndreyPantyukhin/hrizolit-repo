# Хризолит — оформление заказа: передача контекста (для чата по лояльности)

Проект: интернет-магазин «Хризолит» на 1С-Битрикс («Управление сайтом»), шаблон сайта `omegait_design`.
Документ описывает, что сделано в оформлении заказа, как это устроено и куда подключать систему лояльности.
Всё, что помечено **«не проверено»**, написано без доступа к живому Bitrix и требует проверки на staging.

---

## 1. Роль и правила работы (как договорились)

- Роль: старший разработчик Bitrix; классический подход: кастомизация через шаблоны компонентов в `/local/`, события, `init.php`. Правки в `/bitrix/` недопустимы.
- Приоритеты: безопасность → совместимость с обновлениями → производительность → читаемость.
- Не придумывать то, чего нет в макетах: говорить об этом и решать вместе.
- Перед правками на проде: бэкап и проверка на staging. Все ID и настройки — не хардкодом, а через конфиг.
- Дизайн-система: `HRIZOLIT_DESIGN.md` (файл проекта). Шрифты Inter и Lora подключены в `header.php`.

## 2. Что такое проект «оформление заказа»

Утверждённый заказчиком макет (PDF «Сценарии доставки и самовывоза», 28.10.2026): корзина → окно «Выберите способ получения» (Доставка / Самовывоз) → три шага на одной странице:

| Шаг | Сценарий «Доставка» | Сценарий «Самовывоз» |
|---|---|---|
| 1 | Курьером / В пункт выдачи (ПВЗ) / В постамат (СДЭК) | Список магазинов города (ID службы 3) |
| 2 | Ваши данные: ФИО, телефон, email, комментарий | то же |
| 3 | Способ оплаты (из админки) | то же |

На всех шагах справа сайдбар: «Сводка заказа» (количество, итого, доставка, промокод, адрес магазина, плашка про бесплатную доставку от 15 000 ₽ только для курьера) и «Программа лояльности» (пока статичная карточка для гостей). Внизу фиксированная панель: согласие на ПД (шаги 2 и 3), кнопка шага, «N из 3», степпер.

Решения: **вариант А** — заказ создаётся по кнопке «Оплатить» на шаге 3 (штатный `saveOrderAjax`), платёжная система выбирается внутри заказа; после создания идёт редирект на `?ORDER_ID=…` → `confirm.php` с автопереходом в ЮKassa/ЮMoney.

- Корзина: `bitrix:sale.basket.basket`, локальная копия шаблона **`divided-basket`**.
- Все файлы в архиве лежат по боевым путям (`local/templates/omegait_design/components/bitrix/...`).

### Настройки в админке, без которых работа некорректна

- Параметры вызова компонента: `SHOW_DELIVERY_LIST_NAMES=Y`, `SHOW_PAY_SYSTEM_LIST_NAMES=Y`. Остальное (купоны, карты) принудительно выставляет `hz-bootstrap.php`.
- Типы плательщиков: лучше оставить на сайте только «Физическое лицо» (JS скрывает выбор, но чище настроить в админке).
- Свойства заказа: `ADDRESS` (обязательное) показывается только для курьера (ID 79); для ПВЗ/постамата/самовывоза сделать необязательным или привязать только к службе 79, иначе скрытое обязательное поле блокирует сохранение без видимой ошибки. `STREET`, `BUILDING`, `ZIP` и др. адресные подсвойства в форме не показываются: не должны быть обязательными.
- Платёжные системы: состав и порядок на шаге 3 зависят от ограничений каждой системы (по службам доставки, сумме, типу плательщика, сайту и т.д.). У наложенного платежа СДЭК есть собственная настройка в модуле ipol.sdek.

## 4. Как устроено (важно для интеграции)

**Движок.** Штатный `sale.order.ajax` — аккордеон: при каждом refresh перерисовывает все секции в DOM. Блоки: `#bx-soa-region` (местоположение, индекс, тип плательщика), `#bx-soa-delivery`, `#bx-soa-pickup`, `#bx-soa-paysystem`, `#bx-soa-properties` (ФИО, телефон, email, комментарий), `#bx-soa-basket` (скрыт), `#bx-soa-total` (сайдбар).

**Что переопределено в `hz-checkout.js`** (методы экземпляра, `order_ajax.js` не правится; после обновления модуля `sale` нужен регресс):
- `editSection` — все секции отрисованы как «активные» (плоский режим); `fade`, `show`, `getBlockFooter`, `switchOrderSaveButtons`, `totalBlockScrollCheck/ResizeCheck`, `editFade{Region,Props,Delivery,PaySystem,PickUp}Content` — заглушки. Последние обязательны: иначе `locationsCompletion()` после каждого refresh затирает раскрытые секции свёрнутой сводкой.
- `editOrder` — после штатной отрисовки: `hzDecorateRows` (data-атрибуты и порядок строк по `CODE`, скрытие типа плательщика), `hzDecorateDelivery`, `hzDecoratePaySystem`, `hzEnsureDelivery`, `hzApplyStep`, `hzRenderSummary`.
- `editTotalBlock` — после штатного рисует «Сводку заказа» (`hzRenderSummary`).
- `selectStore` — после выбора магазина вручную обновляет сводку (refresh при этом не происходит).
- Мастер: `hzGo`, `hzNext`, `hzValidateStep` (валидация через штатные `isValidRegionBlock`/`isValidProperty`), `hzApplyStep` (показ секций/строк по шагу; элементы каркаса с `data-hz-for`, `data-hz-scenario`), `hzRenderBar`, `hzRenderStepHead`, `hzStepReady`; история `#step-N`.
- Конфиг и тексты приходят из PHP в `BX.Sale.OrderAjaxComponent.params.HZ_CFG` (`scenario`, `delivery`, `freeFrom`) и `.HZ_MESS`.

**Видимость строк свойств по шагам** задаётся картами `ROW_STEP`, `ROW_ORDER`, `ROW_HALF`, `ROW_COURIER_ONLY`, `HIDDEN_CODES`, `LABELS` в начале `hz-checkout.js`. Строки находятся по `data-property-id-row`, `CODE` берётся из `result.ORDER_PROP.properties`.

**Сохранение заказа.** Кнопка `[data-save-button]` (в `hz-bar.php`, видна на шаге 3) → штатный `clickOrderSaveAction` → `isValidForm()` (проверяет в том числе скрытые строки) → событие `bx-soa-order-save` (согласие на ПД) → `doSaveAction` → `sendRequest('saveOrderAjax')` → редирект `?ORDER_ID=…` → `confirm.php`.

**Сценарий** передаётся из корзины параметром `?hz_delivery=delivery|pickup` (белый список). Без параметра — «delivery».

## 5. Куда подключать систему лояльности

Бизнес-задача (со слов заказчика): после ввода номера телефона отправляется запрос в 1С, оттуда приходит процент скидки. Решение по способу применения скидки к заказу ещё **не принято**. Ниже — точки входа и вопросы.

**Клиент (форма):**
- Поле телефона: `[data-hz-code="PHONE"] input` (шаг 2; маска `+7 (___) ___-__-__` из макета **ещё не сделана**). Строки перерисовываются при каждом refresh, поэтому обработчики вешать делегированием или в `hzDecorateRows`.
- Сайдбар: сводка рисуется в `hzRenderSummary()` (`hz-checkout.js`), карточка «Программа лояльности» — `hz-aside.php` (сейчас статичная, только для гостей, текст «Войдите в личный кабинет…»; в макете у неё нет состояния «скидка применена»).
- Пересчёт заказа: `BX.Sale.OrderAjaxComponent.sendRequest()`; в запрос попадают все поля формы (`getAllFormData`), значит, скрытое поле/параметр в форме уедет на сервер.

**Сервер:** запрос в 1С — только с сервера (ключи в `.settings.php`/окружении, не в JS). Варианты применения скидки (выбрать и согласовать): правило скидки на корзину/заказ (sale discount), купон, программная корректировка цены (события `sale`: `OnSaleComponentOrderUserResult`, `OnSaleComponentOrderCreated`, `OnSaleComponentOrderResultPrepared`, `OnSaleOrderBeforeSaved`, названия и сигнатуры сверить с документацией вашей версии). Нужно, чтобы скидка отражалась в сводке, итоге, заказе и в выгрузке в 1С.

**Вопросы лояльности (открыты):** идентификация покупателя (только телефон или ещё и профиль); поведение при недоступности 1С (таймаут, повторы, кэш); нормализация и валидация телефона; защита эндпоинта (`check_bitrix_sessid()`, лимит запросов, не раскрывать факт существования клиента); как показывать скидку в корзине; макет состояния карточки «Программа лояльности»; что показывать авторизованным.

## 6. Известные ограничения и открытые задачи

1. **ПВЗ/постамат СДЭК (ipol.sdek).** Интерфейс выбора пункта живёт в карточке описания выбранной доставки (`.bx-soa-pp-desc-container`), которая теперь показывается. Не сделано: признак выбранного пункта, блокировка «Ваши данные» до выбора, адрес пункта в шапке шага и сайдбаре (`hzStepReady`, `hzDeliverySummary`, `cfg().pvzChosen`). Нужны свойства `IPOLSDK_*` после выбора пункта и версия модуля.
2. **Адрес курьера.** Модуль СДЭК для курьера (ID 79) свой выбор адреса, по-видимому, не показывает; пока на шаге 1 выводится штатное поле `ADDRESS` («Адрес доставки»). Решить окончательно.
3. Маска телефона; мобильная версия (макета нет); стили ошибок валидации; поле промокода (штатный блок купона) и виджет местоположения требуют доводки по стилям.
4. Нижняя панель: на скриншотах пользователя степпер выглядел обрезанным слева. Не выяснено, это обрезка скриншота или отступ.
5. «Новосибирская область» не подставляется в местоположение (регион); покупатель выбирает населённый пункт сам. Код для «Мирный» взят по Якутии (`0001054105`) — подтвердить.
6. `result_modifier.php`: вынести ID `'3'` в конфиг, убрать N+1 (`CCatalogStore::GetList` в цикле), добавить `Loader::includeModule('catalog')`, перенести клиентский патч фильтра складов из `order_ajax.js` на сервер (для гостей и авторизованных одинаково), читать куку через `getCookieRaw`.
7. `header.php`: jQuery подключается дважды, зависимости с `unpkg.com` без SRI, запрос к инфоблоку в шапке без кэша — вне задачи, но стоит учесть.
8. Не проверено: PHP-файлы (`confirm.php`, `hz-*.php`, `hz_checkout.php`) не проходили линтер; событие `OnSaleComponentOrderProperties` — сигнатура и момент вызова взяты по памяти.
9. Отклонения от макета, которые нужно показать дизайнеру: три радио СДЭК вместо двух, поле «Город» (местоположение) на шаге 1, поле «Адрес доставки» для курьера, согласие на ПД, плашка про выходные, поле промокода в сайдбаре, скрытое описание способа оплаты.

## 7. Чек-лист проверки на staging

- Корзина → окно → переход с `?hz_delivery=…` на оформление.
- Сценарий «Самовывоз»: список магазинов (название + адрес), выбор обновляет сайдбар.
- Сценарий «Доставка»: три радио СДЭК, карточка модуля, стоимость в сводке; «Город» подставлен из шапки для гостя.
- Шаг 2: ФИО/телефон/email, комментарий последним; валидация; согласие на ПД.
- Шаг 3: способы оплаты из админки; «Оплатить» создаёт заказ и ведёт на `confirm.php` с автопереходом в ЮKassa; «При получении» — на страницу с итогами.
- «Изменить/Назад»: введённое не пропадает; смена доставки обновляет список оплат.
- Консоль без ошибок; нет строк `hz-checkout:` с предупреждениями; интеграции СДЭК продолжают считать цену.
